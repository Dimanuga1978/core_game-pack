# TableCore v2 — Инструкция администратора

Всё в этом документе реально проверено запуском в этом же репозитории. Каждая команда выполнена минимум дважды: в рабочей директории и в полностью чистой, изолированной копии (`rm -rf node_modules && npm install`).

Обсуждённые, но не реализованные идеи — в `ROADMAP.md`.

---

## Самый быстрый способ — один скрипт, ничего печатать не нужно

Если не хотите разбираться в переменных окружения и отдельных командах — просто запустите:

- **Windows** — дважды кликните `start.cmd` (или запустите его из любой директории — сам найдёт свою папку).
- **Linux/macOS** — `./start.sh`

Скрипт сам: поставит зависимости при первом запуске (если `node_modules` ещё нет), сгенерирует случайный секрет, поднимет **и сервер, и лаунчер** вместе, откроет браузер на лаунчере. На Windows сервер и лаунчер открываются каждый в своём окне — закройте окна, чтобы остановить. На Linux/macOS оба останавливаются по `Ctrl+C` в том же терминале.

**Доступность в локальной сети.** Скрипт сам биндит сервер и лаунчер на все сетевые интерфейсы (`0.0.0.0`), не только на `127.0.0.1` — иначе они были бы видны только с той же машины, что бесполезно для тестирования с реальными людьми на других устройствах в той же Wi-Fi/локальной сети. В консоли при старте будет показан реальный IP-адрес в сети (например, `http://192.168.1.42:4170`) — именно эту ссылку и стоит давать другим тестировщикам, `127.0.0.1` у них не сработает. Admin API **сознательно** остаётся только на `127.0.0.1` — он умеет создавать матчи и выдавать токены, это не то, что должно быть доступно чужим машинам в сети.

**Чтобы создать матч** — откройте `http://127.0.0.1:4181/` в браузере (тоже печатается в консоли при старте). Выберите игру, добавьте игроков, при желании назначьте боту одного из них — получите готовые ссылки и QR-коды на каждого человека-игрока. Подробнее — в разделе 2.1 ниже.

По умолчанию подключены демо-игры репозитория (`tools/server/example.config.mjs`) — если нужен голый движок без игр, задайте `TABLECORE_SERVER_CONFIG` пустым перед запуском, либо используйте ручной способ ниже.

Остальной раздел — то, что делает этот скрипт «под капотом», если нужно больше контроля (свой конфиг игр, отдельный запуск только сервера или только лаунчера, продакшн-настройки).

## 1. Что установить

- **Node.js 20 или новее** (разработка и вся проверка велись на Node v22.22.2; используются нативный test runner, `structuredClone`, `worker_threads` с `resourceLimits`, npm workspaces, нативный браузерный `WebSocket`).
- **npm** (идёт вместе с Node).

Внешний реестр не обязателен — весь движок и все игры лежат в самом репозитории. Системных зависимостей, баз данных, отдельных сервисов не требуется. Единственная внешняя npm-зависимость на весь проект — `immer`.

### Установка

```bash
cd tablecore
npm install
```

Разворачивает **npm workspaces** — 23 внутренних пакета (`packages/*`, `games/*`) становятся настоящими установленными зависимостями друг друга через символлинки в `node_modules/@tablecore/*`.

### Проверка

```bash
npm test
```

Ожидаемо: **295 тестов, 295 pass, 0 fail**. Упало сразу после установки — проверьте `node -v` (нужно 20+).

## 2. Как запускать

### 2.1. `npm run server` — реальный игровой сервер

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # сгенерировать секрет
TABLECORE_SERVER_SECRET="<результат выше>" npm run server
```

Без `TABLECORE_SERVER_SECRET` (короче 32 символов) сервер **откажется стартовать** — намеренно.

**Движок ничего не знает ни об одной игре.** По умолчанию сервер стартует с пустым реестром игр — это не баг и не временное состояние, это принцип: `tools/server/start.mjs` не содержит ни единого импорта конкретной игры. Игры подключаются только через внешний конфиг-файл:

```bash
TABLECORE_SERVER_SECRET="..." TABLECORE_SERVER_CONFIG=path/to/my.config.mjs npm run server
```

где `my.config.mjs` — обычный ES-модуль вида:
```js
export const games = {
  'my-game': myGamePack.game,
};
```

Для демонстрационных игр репозитория есть готовый пример — `npm run server:demo` (эквивалент `TABLECORE_SERVER_CONFIG=tools/server/example.config.mjs npm run server`). Этот файл — **не часть движка**, обычный пример, единственное место, где имена демо-игр вообще появляются.

Без конфига сервер стартует и полностью работает (admin API отвечает, WS-сервер поднят), просто `/api/games` вернёт `[]`, а любая попытка создать матч — `UNKNOWN_GAME_ID`.

```
TableCore admin API:   http://127.0.0.1:4181  (создание матчей, выдача токенов — держите вне публичного интернета)
TableCore game server: ws://127.0.0.1:4180  (сюда подключаются игроки)
Registered games: grid-duel, coin-race, phase-quest, sector-expedition, last-sector
```

Два разных порта намеренно: admin API создаёт матчи и выдаёт токены — держите за файрволом. Игровой WS-порт — то, к чему подключаются игроки.

#### Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `TABLECORE_SERVER_SECRET` | да | — | Секрет подписи токенов, ≥32 символа |
| `TABLECORE_SERVER_CONFIG` | нет | — (сервер без игр) | Путь к конфигу, экспортирующему `{ games }` |
| `TABLECORE_SERVER_HOST` | нет | `127.0.0.1` | Адрес игрового WS-сервера |
| `TABLECORE_SERVER_PORT` | нет | `4180` | Порт игрового WS-сервера |
| `TABLECORE_SERVER_ADMIN_HOST` | нет | = `TABLECORE_SERVER_HOST` | Адрес admin API |
| `TABLECORE_SERVER_ADMIN_PORT` | нет | `4181` | Порт admin API |
| `TABLECORE_SERVER_TOKEN_TTL_SECONDS` | нет | `3600` | Время жизни токенов |
| `TABLECORE_LAUNCHER_URL` | нет | автоопределяется | Базовый URL лаунчера — нужен для join-ссылок и QR-кодов (см. ниже). По умолчанию сервер сам подставляет реальный LAN IP, если сам биндится на `0.0.0.0` (как в `start.sh`/`start.cmd`) — задавайте вручную только если лаунчер запущен на другом порту/хосте, чем по умолчанию. |

#### Самый простой путь — из лаунчера, без единой команды

1. Откройте лаунчер (`http://127.0.0.1:4170`, тоже печатается в консоли при старте), выберите игру, нажмите **«Играть»**.
2. Откроется страница создания игры уже с выбранной игрой — укажите только число игроков (по умолчанию 4) и нажмите **«Создать»**.
3. Сразу на экране — **одна** общая ссылка и QR-код. Отправьте или покажите всем игрокам сразу — сканирование или переход по ссылке автоматически распределяет их по местам, по порядку («кто первый подключился — тот и первый игрок»).
4. Игроки видят страницу ожидания с живым счётчиком «Подключилось: X из Y» — обновляется каждые полторы секунды, ничего обновлять вручную не нужно.
5. Вы тоже видите этот статус на своей странице. Когда решите, что пора — два варианта:
   - **«Начать с N игроками»** — просто начать с тем, что есть, без ботов вообще (если правила игры позволяют такое число — иначе честная ошибка, а не тихий сбой).
   - **«Добавить ботов и начать»** (видна, только если у игры вообще есть боты) — оставшиеся пустые места заполняются ботами со случайно выбранной стратегией на каждое.
6. Игра стартует для всех сразу — у всех подключившихся страница ожидания сама переключится на реальную игру.

**Важно: до шага 6 настоящего матча ещё не существует.** Страница ожидания ничего не знает про саму игру — просто ждёт и опрашивает статус по HTTP. Реальный матч и реальные токены создаются только в момент нажатия «Начать», с финальным списком тех, кто реально подключился (плюс боты, если выбрали).

**Если у игры нет интерфейса** (`grid-duel`, `coin-race`, `phase-quest`, `sector-expedition` — чисто бэкенд-фикстуры для разработки движка, сегодня интерфейс есть только у `last-sector`) — страница честно предупредит и заблокирует создание, а не выдаст ссылку, которая откроется с `404`.

**Про QR-код.** Полная ссылка с настоящим токеном — больше 300 символов, слишком длинно для маленького и надёжно сканируемого кода. QR кодирует короткий адрес вида `http://<хост>:4170/j/AB12CD`, который лаунчер сам резолвит и делает редирект (`302`, не кэшируется браузером специально — иначе разные люди по одной ссылке могли бы попасть на одно и то же место). Сама генерация — собственный код без внешних зависимостей (`packages/qrcode`), проверенный настолько строго, насколько возможно без реальной камеры. Реальную сканируемость телефоном проверьте один раз сами перед тем, как раздавать людям.

Если открыть страницу создания напрямую (`http://127.0.0.1:4181/`, без перехода из лаунчера) — появится выбор игры вручную, дальше всё так же.

#### Создать матч и получить ссылку для игрока (curl, вручную)

```bash
curl -X POST http://127.0.0.1:4181/api/matches \
  -H "content-type: application/json" \
  -d '{"gameId":"last-sector","players":["A","B"],"options":{"seed":7},"spectatorPolicy":"public"}'
```

Ответ содержит `matchId`, токен на каждого игрока, `wsUrl`. По умолчанию `spectatorPolicy:"deny"`.

Ссылка для игрока A (лаунчер раздаёт статику, см. 2.2):

```
http://127.0.0.1:4170/games/last-sector/player-ui/index.html?match=<matchId>&player=A&token=<токен A>&ws=ws://127.0.0.1:4180
```

Игрок открывает ссылку — клиент сам подключается, аутентифицируется токеном, синхронизируется. Полностью проверенный поток (см. `CLIENT_LAYER_FIX.md`).

Токен зрителя: `curl -X POST http://127.0.0.1:4181/api/spectator-tokens`

#### Игра против бота

Любого игрока в матче можно сделать ботом:

```bash
curl -X POST http://127.0.0.1:4181/api/matches \
  -H "content-type: application/json" \
  -d '{"gameId":"last-sector","players":["A","B"],"bots":{"B":"aggressive"}}'
```

Сервер начинает автоматически водить B сразу после создания матча — включая живые обновления всем подключённым (человек видит ходы бота в реальном времени). В ответе `tokens` — только токены **людей**, токен бота никогда не покидает сервер.

`GET /api/games` возвращает `bots: [...]` на каждую игру — какие стратегии доступны. Сегодня реальные стратегии (`random`, `aggressive`) есть только у `last-sector`. Запрос бота у игры без стратегий отклоняется явно (`UNKNOWN_BOT_STRATEGY`), не тихо игнорируется. Можно сделать матч полностью автономным (все игроки — боты) — ответ `tokens` будет `{}`.

Если стратегия бота ломается (кидает исключение раз за разом) — сервер отключает её после `botMaxConsecutiveFailures` (по умолчанию 5) подряд неудач, не зацикливается и не роняет сервер.

#### Какие игры доступны

**Ни одной по умолчанию.** Движок не содержит ни одного упоминания конкретной игры нигде в своём коде — ни в `packages/*`, ни в `tools/server/start.mjs`, ни в `tools/launcher/`. Игры подключаются исключительно через `TABLECORE_SERVER_CONFIG` (см. выше). Единственный способ узнать, «какие игры доступны» — посмотреть, что перечислено в конкретном используемом конфиге.

**Из демо-игр репозитория** (доступны через `npm run server:demo`) **реально играбельна сегодня только `last-sector`** — у остальных четырёх никогда не было браузерного клиента (чисто бэкенд-фикстуры при разработке движка). Правила/сервер/протокол у всех пяти рабочие — не хватает именно UI. У `last-sector` теперь работает и `player-ui` (управление), и `tv-ui` (доска для зрителей/трансляции, read-only) — **полная версия**, с камерой, визуальными эффектами и choreographed-последовательностями (не упрощённая), построена поверх уже готовой декларативной схемы в `games/last-sector/client/presentation.js`. Общая, игро-независимая часть этой системы (`FxRuntime`, `PresentationCamera`, `PresentationSequenceRuntime`, `PresentationDispatcher`, `OnboardingRuntime`) — отдельный движковый пакет `@tablecore/presentation-client`, отдаётся лаунчером по `/presentation-client/*`, 48 тестов, включая полный сквозной прогон реальных данных игры через реальный стек рантаймов.

### 2.2. `npm run launcher` — библиотека игр

```bash
npm run launcher
```

`http://127.0.0.1:4170` — карточки всех игр из `games/*/manifest.json`. Переменные: `TABLECORE_LAUNCHER_HOST`, `TABLECORE_LAUNCHER_PORT`.

Лаунчер не создаёт матч и не выдаёт токен — чистая раздача статики (`player-ui/`, `preview/`, `tv-ui/`, `client/`, обложка; плюс `/engine-client/*` — общая, движковая клиентская библиотека `@tablecore/browser-client`, одна на все игры, не дублируется по каждой игре отдельно; всё остальное недоступно намеренно).

**Связь с созданием матча.** На каждой карточке игры с интерфейсом (`hasPlay: true`) — отдельная кнопка **«Создать матч»**, рядом с «Играть»/«Превью». Она ведёт на страницу создания матча (раздел 2.1 выше) с уже предвыбранной игрой — не нужно заново искать её в выпадающем списке. Кнопка «Играть» при этом никуда не делась и ведёт себя как раньше (открывает `player-ui` напрямую, без матча) — это два **разных** назначения для двух разных аудиторий, а не дублирование:

- **«Играть»** — для игрока, который просто просматривает лаунчер (в том числе с другого устройства в сети). Открывает страницу — честно покажет предупреждение «нет активного матча», если открыта без реальной ссылки от организатора.
- **«Создать матч»** — для **организатора**, который сидит за той же машиной, где запущен сервер (admin API доступен только с `127.0.0.1` — см. раздел 3). Если игрок на другом устройстве в сети всё же нажмёт эту кнопку — она просто не откроется (admin API недоступен извне), никакой утечки прав не происходит, но и толку тоже нет, поэтому у кнопки есть подсказка при наведении, что она открывается только с машины сервера.

## 3. Безопасность перед продом

- **Секрет** подписывает все токены. Ротация инвалидирует все токены разом — для точечной инвалидации `auth.revoke(sessionId)`, не смена секрета.
- **Admin API не публичен** — держите за файрволом.
- **`spectatorPolicy`** по умолчанию `deny`.
- **TLS** — `createWsServer` принимает `tlsOptions`; для прода проще реверс-прокси с TLS-терминацией.
- **Изоляция матчей — реально воспроизведённый, серьёзный риск, не теория, теперь с реально работающим opt-in решением.** По умолчанию всё в одном процессе (`ServerHost`), нулевой риск для существующих развёртываний. Проверил напрямую: синхронный бесконечный цикл внутри `applyActionInPlace` **любой** зарегистрированной игры (не обязательно злонамеренной — обычный баг в чужом game-пакете тоже подходит) навсегда замораживает весь процесс для **всех** матчей и **всех** игроков одновременно — не крах с восстановлением через рестарт, а зависание без единого исключения, которое ничто не прерывает извне.

  **Решение подключено и подтверждено живым тестом.** `createTableCoreServer` теперь принимает опцию `matchHost` — передайте настоящий `new MatchWorkerPool({ poolSize, rpcTimeoutMs })` вместо дефолтного `ServerHost`, и CPU-watchdog (`rpcTimeoutMs`) реально ограничивает радиус поражения одним worker'ом вместо всего процесса. Проверено не в теории: реальный сервер, реальный зависающий матч (`games/infinite-loop-test`) — совершенно не связанный, здоровый матч на другом worker'е продолжает синхронизироваться и принимать реальные действия, admin API остаётся отзывчивым.

  Компромисс, который стоит понимать перед включением: один worker обслуживает несколько матчей одновременно (маршрутизация по хэшу matchId) — при убийстве зависшего worker'а теряются **все** матчи на нём, не только виновный (без персистентности восстановить нечем). Настраивается через `poolSize` — больше worker'ов, меньше матчей на каждый, но больше накладных расходов на потоки. Реальные накладные расходы на каждый вызов (сериализация через границу потока) тоже есть, хоть и небольшие для типичного размера состояния пошаговой игры.

  Игры для worker-режима нужно регистрировать с обоими полями одновременно — и живым объектом (`game`, нужен ботам, которые принимают решения в главном потоке через `getLegalActions`), и путём к модулю (`gameModuleUrl`/`gameExportName`, нужен worker'у для независимого импорта — worker не может получить живую JS-ссылку из основного потока, отдельный V8-isolate):
  ```js
  createTableCoreServer({
    games: {
      'last-sector': {
        game: lastSector,
        gameModuleUrl: new URL('../games/last-sector/src/index.js', import.meta.url).href,
        gameExportName: 'lastSector',
      },
    },
    matchHost: new MatchWorkerPool({ poolSize: 4, rpcTimeoutMs: 2000 }),
  });
  ```
  Честное, задокументированное ограничение: `sweepExpiredMatches` (очистка жизненного цикла, см. ниже) у `MatchWorkerPool` пока не реализован — worker-режим не получает автоматической очистки завершённых матчей, только жёсткий потолок `maxMatches`.
- **Rate limiting/backpressure** уже встроены в транспорт, настраиваются через опции `createWsServer`.
- **Страница создания матча (`/`) и файлы QR-библиотеки (`/qrcode/*`) намеренно доступны без `X-Admin-Key`**, даже если ключ настроен — иначе саму страницу нельзя было бы открыть обычным переходом по ссылке (заголовок не передать через простую навигацию браузера). Реальные вызовы API (`/api/matches`, `/api/games` и т.д.) по-прежнему требуют ключ; страница передаёт его сама через `?key=` в своём URL. Раздаётся только статика — ни один из этих путей не даёт доступа к данным матчей.
- **Очистка завершённых матчей.** Раньше матч, однажды созданный, оставался в памяти навсегда — `maxMatches` только не давал создавать новые сверх потолка, но никогда не освобождал место от старых. Теперь `ServerHost` умеет `sweepExpiredMatches()`, и реальный сервер вызывает его периодически сам. Настраивается через опции `createTableCoreServer`: `matchSweepIntervalMs` (по умолчанию 5 минут; `0` отключает периодическую очистку целиком), `matchFinishedGraceMs` (сколько завершённый/прерванный матч ещё виден после окончания — по умолчанию 30 минут), `matchAbandonedLobbyGraceMs` (сколько живёт матч, застрявший в `lobby` из-за неудачного старта — по умолчанию час). Матчи в статусе `running` не удаляются никогда, независимо от простоя — это намеренно оставлено на усмотрение конкретного развёртывания, а не решается движком автоматически.

## 4. Диагностика

- **`npm test` падает после установки** — версия Node.
- **Сервер не стартует** — секрет отсутствует/короче 32 символов.
- **Игрок не подключается** — токен истёк, `ws=` не совпадает с реальным адресом, или `match=` не существует.
- **`MATCH_ACCESS_DENIED` у зрителя** — матч без `spectatorPolicy:"public"`, это по умолчанию.
- **Нет кнопки «Играть»** — у игры нет `player-ui/index.html` (сегодня верно для четырёх из пяти игр).
- **QR-код не сканируется** — сама логика (данные внутри кода) проверена строго автоматическими тестами, но реальную сканируемость камерой я проверить не могу (см. раздел про создание матча выше). Если не сканируется — используйте кнопку «Копировать» рядом с QR-кодом как запасной вариант, ссылка работает в любом случае.
- **Короткая ссылка `/j/...` не открывается / `502 ADMIN_API_UNREACHABLE`** — лаунчер не может достучаться до admin API. Обычно значит, что сервер (`npm run server`/`start.sh`/`start.cmd`) не запущен, либо `TABLECORE_ADMIN_API_URL` у лаунчера указывает не туда (по умолчанию `http://127.0.0.1:4181` — верно, если оба процесса на одной машине, как при обычном запуске).
- **В `joinLinks`/QR-коде подставлен неправильный/недоступный адрес** — проверьте `TABLECORE_LAUNCHER_URL`, если задавали его вручную; при автоопределении сервер сам подставляет реальный LAN IP, когда сам биндится на `0.0.0.0`.

## 5. Что было найдено при жёстком аудите перед реальными людьми

Отдельный документ `HARD_AUDIT_BEFORE_REAL_USERS.md` содержит полный разбор. Коротко — три критичные, реально воспроизведённые находки, все исправлены и закрыты тестами:

1. **Полное падение сервера через OOM.** `{"gridWidth":100000,"gridHeight":100000}` в `options` у Last Sector гарантированно валил весь Node-процесс. Один игрок мог положить сервер для всех. Исправлено — потолок на реальных замерах (40×40, ~160мс).
2. **Произвольное чтение файлов с сервера.** `options.scenario` уходил в `path.join()` без проверки — `../../../package` реально читал корневой `package.json` репозитория, и содержимое утекало в возвращённый игровой state. Исправлено — строгий формат id + containment-проверка пути.
3. **Admin API был полностью не защищён** — ни аутентификации, ни rate limiting, ни потолка на число матчей. Добавлено всё три, плюс убрана утечка текста исключений в ответах клиенту.
