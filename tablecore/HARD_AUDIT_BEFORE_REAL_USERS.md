# Жёсткий аудит движка и подключения игр перед реальными людьми

Задача: максимально агрессивно проверить код и архитектуру, подключить ботов. Всё ниже — реально воспроизведено, не теория.

---

## Критические находки (реальные, воспроизведённые PoC)

### 1. Полный крах сервера через OOM

**Where:** `games/last-sector/src/legacy/game.cjs`, `options.gridWidth`/`options.gridHeight`.

Оба поля читались из пользовательского `options` без верхней границы: `w: +options.gridWidth || 9`. Проверил напрямую:

```js
lastSector.createInitialState({ players:['A','B'], seed:1, gridWidth: 100000, gridHeight: 100000 })
```

Результат — `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory`, процесс аварийно завершается через ~47 секунд. Один запрос через admin API (`POST /api/matches`) — и сервер лежит для всех подключённых игроков одновременно.

**Фикс:** потолок `MAX_GRID_DIMENSION = 40`, выбранный не наугад, а по реальным замерам:

| Размер | Клеток | Время |
|---|---|---|
| 20×20 | 400 | 48мс |
| 30×30 | 900 | 84мс |
| 40×40 | 1600 | 160мс ← выбранный потолок |
| 50×50 | 2500 | 327мс |
| 70×70 | 4900 | 1124мс |
| 100×100 | 10000 | 4549мс |
| 100000×100000 | — | OOM crash |

По пути обнаружил, что сама генерация карты нелинейна (похоже на O(n²) от `Array.indexOf` внутри цикла размещения типов клеток в legacy-коде) — не стал рискованно переписывать чужую, уже проверенную логику под давлением времени; вместо этого выбрал безопасный потолок эмпирически, а не теоретически.

### 2. Произвольное чтение файлов с сервера

**Where:** `games/last-sector/scenarios/legacy.cjs`, `options.scenario`.

```js
const file = path.join(__dirname, `${key}.json`);
if (!fs.existsSync(file)) throw ...
```

`path.join` не защищает от `../`-обхода — классическое заблуждение. Проверил:

```js
lastSector.createInitialState({ players:['A','B'], seed:1, scenario: '../../../package' })
```

Результат — реально прочитал `package.json` из корня репозитория, и его содержимое оказалось внутри возвращённого игрового state (то есть потенциально утекло бы в state, отправляемый игрокам через WS). Полноценный LFI (local file inclusion), достижимый через admin API с любыми `options`.

**Фикс:** та же containment-проверка, что уже доказала себя в лаунчере несколько проходов назад, плюс строгий формат id (`/^[A-Za-z0-9_-]{1,64}$/`). Проверил на пяти вариантах обхода (`..%2f`, `....//....//`, null-байты, абсолютные пути) — все заблокированы, легитимный сценарий по-прежнему работает.

### 3. Admin API был полностью не защищён

Ни аутентификации, ни rate limiting, ни потолка на число матчей. Добавлено:

- **`X-Admin-Key`** — опциональный (не обязательный, чтобы не усложнять чисто локальный запуск), но настоятельно рекомендуемый заголовок.
- **Rate limiting по IP** — 20 запросов/минуту по умолчанию, тот же sliding-window паттерн, что уже используется в WS-транспорте.
- **`maxMatches`** — жёсткий потолок (1000 по умолчанию). `ServerHost` никогда не удаляет завершённые матчи из памяти — без потолка это медленная утечка на длительном запуске.
- Убрана утечка сырых текстов исключений в ответах клиенту.

## Побочная находка: `createWsClient` тоже игнорировал `host`

При написании бот-клиента обнаружил тот же класс бага, что уже чинил для `createWsServer.listen()`: `createWsClient({port, host, ...})` принимал `host`, но полностью игнорировал его — обе ветки были жёстко захардкожены на `127.0.0.1`. Не проявлялось раньше, потому что все существующие тесты и так использовали дефолтный `127.0.0.1`. Исправлено тем же паттерном, покрыто отдельным regression-тестом.

## Интеграция ботов

### Архитектура

Реестр игр принимает либо голый game-объект (боты недоступны, обратная совместимость), либо `{game, bots}` — тот же формат, что уже используют паки. Движок по-прежнему не знает ни одного конкретного имени игры или стратегии — это решает исключительно конфиг.

**Ключевое решение:** решение бота принимается на сыром, авторитетном state через `matchHost.getAuthoritativeState()` — не на спроецированном. Та же причина, по которой `availableActions` в снапшоте вычисляется на сыром state: функции ботов ожидают внутреннее представление, отличающееся от клиентской проекции.

**Отправка действия бота** идёт через настоящее WS-подключение — не прямой вызов `submitAction()`. Прямой вызов обновил бы state, но не разослал бы `UPDATE` подключённым людям (широковещательная логика приватна внутри `createWsServer`). Подключаясь как настоящий клиент, бот бесплатно переиспользует всю уже протестированную логику рассылки.

**Защита от зависания:** каждое действие бота идёт через `setImmediate` — не синхронный tight loop. Цепочка ходов бота не блокирует event loop для остальных матчей.

**Защита от сломанной стратегии:** после `botMaxConsecutiveFailures` (по умолчанию 5) подряд неудач матч перестаёт водиться автоматически. Проверено вживую — сервер остаётся отзывчивым даже со сломанной стратегией.

### Проверено вживую

```
match created: match-...  bots: {"B":"aggressive"}  human tokens: ["A"]
A synced, version: 1  activePlayer: A
[A завершает ход]
total UPDATE messages A received: 5
  version 2  activePlayer now: B
  version 3  activePlayer now: B
  version 4  activePlayer now: B
  version 5  activePlayer now: B
  version 6  activePlayer now: A
```

A ни разу не отправлял больше одного сообщения — все ходы бота произошли автоматически, живые UPDATE пришли на каждый ход.

### Использование

```bash
curl -X POST http://127.0.0.1:4181/api/matches \
  -H "content-type: application/json" \
  -d '{"gameId":"last-sector","players":["A","B"],"bots":{"B":"aggressive"}}'
```

`GET /api/games` возвращает `[{id, bots:[...]}]`. Токены ботов никогда не покидают сервер.
