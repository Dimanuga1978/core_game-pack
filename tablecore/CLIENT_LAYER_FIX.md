# Реальный фикс клиентского слоя Last Sector

## Что было обнаружено

При подготовке пользовательской документации («как играть») попытался честно проверить утверждение из прошлого ответа («last-sector играбельна») — и обнаружил, что оно было основано только на HTTP 200 у HTML-страницы, не на реальной загрузке JS в браузере. При проверке оказалось:

- `player-ui/main.js` и `tv-ui/main.js` импортировали `/client/browser/{player-client,runtime,frame-scheduler}.js` — **не существовали нигде в репозитории**.
- `../client-state.mjs` (`reduceLastSectorEvent`) — **тоже не существовал**.
- Код ожидал `principal: player` (голый id) вместо подписанного токена — несовместимо с реальным протоколом движка, который требует `HELLO`+токен через `createTokenAuth`.
- `runtime.snapshot.availableActions` — сервер вообще не передавал это поле по протоколу.
- `assets.mjs` (существовавший файл) уже был недоступен по HTTP из-за моего же более раннего security-фикса лаунчера (allowlist не включал корень директории игры).
- `tv-ui` оказался сломан заметно сильнее — ссылается на `camera`, `fxRuntime`, `sequenceRuntime`, `onboarding` — системы, которых нет вообще нигде и которые представляют собой отдельный, немаленький объём работы.

## Осознанное решение по объёму

Полноценный фикс `tv-ui` — это отдельная, большая инженерная задача (нужно проектировать и строить camera control, FX runtime, sequence runtime, onboarding flow). Я **не стал** наспех причёсывать это в рамках одной сессии. Сфокусировался на `player-ui` — это то, от чего реально зависит ответ на вопрос «может ли игрок сыграть».

## Что сделано (движок)

**`ServerHost.getSnapshot()` получил `availableActions`** — вычисляется на настоящем, авторитетном `state` (не на спроецированном) через `game.getLegalActions(state, viewer)`, отдельно на каждого viewer. Клиент не может безопасно вычислить это сам — он видит только спроецированную форму state, которая не совпадает с внутренней формой, нужной `getLegalActions`.

## Что сделано (клиентская библиотека Last Sector)

Три реальных файла в `games/last-sector/client/browser/`:
- **`frame-scheduler.js`** — простой rAF-дебаунсер, с фолбэком на `setTimeout` для сред без DOM (тестирование).
- **`player-client.js`** — транспорт+auth слой: открывает WebSocket, отправляет настоящий `HELLO` с подписанным токеном. Отказывается открывать соединение без токена — падает громко, не тихо.
- **`runtime.js`** — оркестратор: полноценная стейт-машина (`connecting → transport-connected → session-ready → connected/resumed → disconnected/connect-error/stopped`), pub/sub (`.on()`), **настоящий reconnect с ограниченным backoff** (не бесконечный tight-loop) — реализует заявленный в манифесте пака capability `'reconnect'`, который раньше не был реализован вообще.

Плюс `games/last-sector/client/client-state.mjs` — редьюсер сырого protocol-снапшота в форму, которую ожидает UI (в основном тонкий passthrough — `state.tiles`/`state.units` уже приходят в нужной форме от `getPlayerView()`, добавляет удобные алиасы `active`/`scores`/`availableActions`).

`assets.mjs` перемещён в `client/` (тот же allowlisted путь), `player-ui/main.js` переключён на новые пути + чтение `?token=` из URL.

## Обходной путь для протокольной логики в браузере

`runtime.js` не может импортировать настоящий `ClientSession` из `@tablecore/protocol` — это bare-specifier, браузер не резолвит такое без import map, которого нигде не настроено. Вместо того чтобы городить import map (что потребовало бы открыть `packages/protocol/src/*` наружу по HTTP — отдельное, более рискованное решение, которое не стал принимать походя), сделал маленькую, явно закомментированную копию нужной логики (`ClientSessionState`, ~20 строк) прямо в `runtime.js` — тот же класс компромисса, что и жёстко прописанный `PROTOCOL_VERSION = 1` в обоих файлах.

## Побочная находка при проверке через реальный лаунчер

`.mjs`-файлы отдавались с `Content-Type: application/octet-stream` — браузер откажется исполнять ES-модуль с таким типом, даже при HTTP 200. Это не поймать проверкой статус-кода, только реальной проверкой заголовков. Починил маппинг расширений в `tools/launcher/server.mjs`.

## Проверено по-настоящему, не только юнит-тестами в изоляции

Node v22 имеет нативный `WebSocket` — значит клиентскую логику (не DOM-код, а протокольную) можно тестировать напрямую, без браузера и без моков:

- Реальный сервер (`createTableCoreServer`) + реальный `PlayerClient`/`ClientRuntime` + реальный WebSocket: подключение, аутентификация, синхронизация, отправка `MOVE`, принятие сервером — всё сквозное.
- Reconnect: реально обрываю сокет, проверяю, что открывается НОВЫЙ сокет и статус переходит в `resumed`, не `connected`.
- `PlayerClient` реально отказывается открываться без токена.
- Устаревшая версия действия реально отклоняется сервером, ошибка реально всплывает в `runtime.on('error', ...)`.
- Через реальный `createLauncherServer` — каждый файл, который импортирует `player-ui`, реально отдаётся с правильным HTTP-статусом и правильным Content-Type.

**295/295 тестов**, дважды с нуля (рабочая директория + изолированная копия без `node_modules`).

## Что осталось честно не сделанным

- **`tv-ui` по-прежнему не работает** — не входил в объём этого фикса, задокументировано явно.
- **Общий `design-system/index.css`**, на который ссылается `player-ui/index.html`, тоже не существует — косметическая деградация (страница использует свой собственный `style.css`, который существует и работает), не блокирует функциональность.
- Иконки/лейблы для `STEAL` в статической карте `ACTIONS` в `main.js` отсутствуют (есть `COLLECT` вместо этого) — кнопка всё равно появится (рендерится по `availableActions` с сервера, не по этой карте), просто с менее точным лейблом. Косметика, не влияет на играбельность.

## Дополнение: архитектурная поправка после прямого вопроса

После того как всё выше было сделано и проверено, поступил закономерный вопрос: «мы сейчас переписываем движок под одну игру, или это применимо ко всем?» Проверил честно — и ответ оказался «и то, и другое, в разных частях этой же работы»:

**Действительно движковые, применимые ко всем играм фиксы** (не менялись):
- `ServerHost.getSnapshot()`'s новое поле `availableActions` — вычисляется через стандартный `game.getLegalActions(state, viewer)`, который обязан реализовать любой пак. Не завязано ни на что специфичное для Last Sector.
- `.mjs` MIME-type фикс в лаунчере — применим к любой игре, использующей `.mjs`-файлы.
- Расширение allowlist лаунчера (`client/`) — общий механизм.

**Найденная и исправленная архитектурная ошибка:** `PlayerClient`, `ClientRuntime`, `FrameScheduler` — три файла клиентской библиотеки — оказались **на 100% движковыми** (проверил: `grep` на упоминания Last Sector внутри файлов — ноль строк логики, одна строка в комментарии, ссылающаяся на пример использования). Но физически я положил их в `games/last-sector/client/browser/` — то есть внутрь папки одной игры. Это прямое нарушение принципа разделения движок/контент, который сам же закреплял в `DISTRIBUTION.md` парой сессий раньше.

**Исправлено:**
1. Три файла перенесены в настоящий движковый пакет `packages/browser-client` (`@tablecore/browser-client`), с собственным `package.json`, зарегистрирован в workspaces.
2. Лаунчер получил новый, узкий, осознанно рассмотренный роут `/engine-client/*`, отдающий **только** этот один пакет (не всё `packages/*` — та же дисциплина, что и в security-фиксе allowlist для игр).
3. `player-ui/main.js` переключён на абсолютный путь `/engine-client/player-client.js` — именно так, как изначально (интуитивно верно) делал присланный патч лаунчера, который я раньше принял за баг из-за отсутствия файлов.
4. **Главное доказательство — не словами, а тестом**: `packages/browser-client/test/genericity.test.js` реально прогоняет тот же `PlayerClient`/`ClientRuntime` против **grid-duel** — совершенно другой игры, с другой формой действий (`{type:'MOVE',direction:'E'}` вместо `{type:'MOVE',to:'q,r'}`) и другой формой state, без единого `stateReducer`. Тест реально проходит: подключение, авторизация, синхронизация, отправка хода, принятие сервером.

**Что осталось специфичным для Last Sector, и это правильно** — `client-state.mjs`'s `reduceLastSectorEvent`. Это единственная часть, которой и положено быть игро-специфичной: адаптер между общим протокольным снапшотом и конкретной формой, которую хочет конкретный UI конкретной игры.

**296/296 тестов**, чисто с нуля, после переноса.

## Второе дополнение: полное отделение движка от игр (по прямому запросу)

После переноса клиентской библиотеки в `packages/browser-client` последовал следующий, более широкий вопрос: «движок вообще не должен ничего знать об играх, у него в коде не должно быть никаких упоминаний конкретных игр — игры просто подключаются». Проверил весь `packages/*` и `tools/*` (вне тестов) на реальные нарушения — нашёл и исправил четыре:

1. **`tools/server/start.mjs`** — статически импортировал все 5 демо-игр и хранил хардкод-реестр `DEFAULT_GAMES`. Переписан: `games` по умолчанию `{}`, реальный плагин-механизм — `TABLECORE_SERVER_CONFIG` (путь к внешнему файлу, читается динамическим `import()` в рантайме). Демо-игры вынесены в `tools/server/example.config.mjs` — единственное место, где их имена вообще появляются, явно помечено как пример.
2. **`tools/launcher/generate-manifests.mjs`** — хардкодил список из трёх игр по именам пакетов и exportName. Переписан на сканирование `games/*` по файловой системе + чтение `package.json` каждой найденной директории — ни одного имени игры в коде. Проверил вживую: удалил `coin-race/manifest.json`, генератор сам его нашёл и восстановил байт-в-байт идентично оригиналу.
3. **`tools/performance/benchmark.mjs` и `broadcast-benchmark.mjs`** — оба напрямую импортировали конкретную игру для нагрузки. Переписаны на generic-раннер с `--target=<путь>`, конкретные цели вынесены в `tools/performance/targets/*.config.mjs` — тот же паттерн «явный, отдельный пример», что и у сервера. Оба реально запущены после рефакторинга и дали осмысленные числа.
4. **Комментарии в `packages/*`** (`browser-client`, `core/runAction.js`, `game-api/index.js`, `protocol/stateVisibility.js`, `server/ServerHost.js`) — упоминали конкретные игры как примеры в объяснениях. Переформулированы абстрактно.

**Тесты переписаны так, чтобы доказывать сам принцип, а не только не ломаться:** новый тест `'with no games supplied, the server starts fully functional but has zero games registered'` создаёт сервер вообще без игр и проверяет, что `/api/games` возвращает `[]`, а попытка создать матч отклоняется `UNKNOWN_GAME_ID` — это не побочный эффект рефакторинга, а прямое, воспроизводимое доказательство того, что движок работает полностью самостоятельно, без единой игры внутри.

Финальный `grep`-sweep по `packages/tools` (вне тестов и явных `*.config.mjs`-примеров) на имена всех пяти демо-игр — пусто.

**298/298 тестов**, дважды с нуля.
