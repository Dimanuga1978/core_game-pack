## P0-1 — E-02: Immer draft lifetime hazard

**Статус: подтверждено буквально, исправлено на уровне статической проверки пака.**

Воспроизвёл точный пример из отчёта:

```js
applyActionInPlace(state) {
  setTimeout(() => { state.value = 999; }, 50);
  return { state, events: [] };
}
```

Результат — реальный `process.exit(1)` с необработанным исключением `TypeError: Cannot perform 'set' on a proxy that has been revoked`. Строка кода после ожидания никогда не выполняется. Это подтверждает вашу оценку точно: `try/catch` вокруг синхронного `produce()` физически не может перехватить исключение, прилетающее на отдельном, более позднем тике event loop — область действия перехвата заканчивается раньше, чем срабатывает `setTimeout`.

**Что сделано:**
- Новая статическая проверка в `pack-linter` (`DEFERRED_SCHEDULING_IN_APPLY_ACTION_IN_PLACE`) — обнаруживает `setTimeout`/`setInterval`/`queueMicrotask`/`setImmediate`/`Promise`/`.then` в исходном тексте `applyActionInPlace` до того, как пак вообще загрузится. Тот же механизм (regex по `Function.prototype.toString()`), что уже применяется для существующей проверки на `structuredClone()` на драфте.
- Проверено на реальной, крупной legacy-функции Last Sector (`applyActionInPlace`, ~250 строк) — **0 ложных срабатываний**.
- 5 новых тестов, включая точный пример из вашего отчёта.
- Заодно исправлен устаревший комментарий в `runAction.js`, ссылавшийся на несуществующий файл `execution.js` — этот же комментарий, судя по всему, был источником одноимённого упоминания в вашем отчёте. Добавлен явный regression-тест, фиксирующий реальный (но не выделенный) механизм отклонения async rule-функций через общую проверку контракта.

**Что не сделано и почему:** не стал добавлять глобальный `process.on('uncaughtException')` в качестве основного механизма защиты — согласен с вашей формулировкой, что это last-resort containment, не граница корректности. Регулярное выражение статической проверки ловит очевидную, текстовую форму ошибки; определённый автор пака теоретически может обойти её через вынесенную функцию-помощник. Ваш пункт про перевод продакшен-пути на `MatchWorkerPool` для непроверенных паков остаётся открытым архитектурным решением — `MatchWorkerPool` уже подключается опционально через `matchHost` (сделано в предыдущей итерации), но не является дефолтом по причине, задокументированной отдельно (несовместимость формата регистрации игр — `gameModuleUrl` vs живой объект). Готов обсуждать перевод на воркер-изоляцию как дефолт для непроверенных паков отдельным треком.

## P0-2 — E-01: RNG seed в состоянии матча

**Статус: подтверждено как структурная проблема, активной утечки на сегодня не обнаружено.**

`match.seed`/`match.rngState` — действительно поля прямо на объекте `match`, как вы указали. Проверил оба реальных пути:
- `ServerHost.getSnapshot()` — явно деструктурирует безопасное подмножество полей (`id, status, players, state, result, version, spectatorPolicy`), не спред всего `match`. Seed физически не попадает.
- `getAuthoritativeState()` (единственное место, отдающее сырое состояние) — вызывается только из внутреннего серверного бот-драйвера. Ни один тип протокольного сообщения (`HELLO`/`SYNC_REQUEST`/`ACTION` — весь набор) не ведёт к этому методу.

Ваша формулировка точна: "текущий код это не эксплуатирует, но полагаться на дисциплину каждого будущего потребителя — не структурная гарантия". Согласен полностью.

**Что сделано:** добавлен сильнейший из практичных regression-тестов — реальный запущенный сервер, реальное WS-соединение, буквальный поиск строк `"seed"`/`"rngState"` (и самого значения seed) в **сыром JSON-тексте** реального `SYNC` и `UPDATE` сообщения, на любой глубине вложенности, а не только на двух конкретных уровнях, которые уже проверялись раньше. Это работает как tripwire: если в будущем какой-то новый код случайно начнёт отдавать `match` целиком, тест немедленно сломается.

**Что не сделано:** не стал вводить отдельный тип/структуру "PlayerFacingMatch" на уровне TypeScript-подобной типизации (в проекте её нет) — учитывая, что единственный реальный путь утечки уже явно деструктурирует нужные поля, а не спредит объект, посчитал введение новой абстракции для не-эксплуатируемой сегодня проблемы избыточным риском. Открыт к пересмотру, если считаете это недостаточным.

## E-06: `startMatch()` context merging

**Статус: подтверждено буквально, исправлено.**

`{ players: match.players, ...match.options, ...context }` — `context` (последний spread) действительно мог переопределить `players`. Проверил: ни один реальный вызывающий код, ни в продакшене, ни в тестах, никогда не передаёт `context` в `startMatch()` — параметр был фактически неиспользуемым, что дало полную свободу исправить без риска регрессии.

**Что сделано:** зарезервированные поля (`players`, `matchId`, `id`, `seed`, `version`, `status`, `events`, `options`) теперь явно вычищаются из `context` перед слиянием; `players` дополнительно ставится последним в spread как defense-in-depth. Два теста: один воспроизводит точную атаку (`context: {players: ['EVIL','HACKED']}`) и подтверждает, что реальный список остаётся нетронутым; второй подтверждает, что легитимное расширение через `context` (нерезервированные поля) по-прежнему работает — сужение примитива, не удаление его функциональности.

## E-04: неограниченный рост истории событий

**Статус: подтверждено буквально, исправлено.**

`next.events = [...match.events, ...events]` действительно накапливается на каждом действии без ограничения. Проверил перед исправлением: `match.events` **нигде в продакшен-коде не читается**, только пишется — `playReplay()` реконструирует партию из отдельного, самостоятельно записанного лога действий (`replay.actions`), не из этого поля. Это дало возможность безопасно ограничить, не рискуя сломать воспроизведение.

**Что сделано:** ограничено до последних 100 событий (не удалено полностью — на случай будущего диагностического потребителя, которому нужна ограниченная недавняя история). 3 теста: реальный прогон 150 действий подтверждает, что массив не превышает лимит; отдельный тест подтверждает, что при ограничении сохраняется именно "хвост" (недавние события), а не "голова"; третий подтверждает, что короткий обычный матч вообще не усекается.

**Что не сделано:** не стал реализовывать полное разделение "живая история / ограниченное окно для диагностики / долговременное хранилище воспроизведения", как предлагает ваша формулировка — это архитектурно более крупная задача (реальный persistence-слой), которую считаю отдельным треком, а не частью этого раунда исправлений. Текущее ограничение снимает и утечку памяти, и O(n²) стоимость копирования, что было конкретной, измеримой проблемой.

## G-02: `Last Sector` — `applyAction()` полностью нерабочий

**Статус: подтверждено эмпирически, исправлено.**

```
lastSector.applyAction(state, {type:'END_TURN', actor:'A'})
→ {"code":"RNG_CONTEXT_REQUIRED"}
```

— для любого легального действия, стопроцентно воспроизводимо. Причина оказалась проще, чем предполагали два варианта решения в вашем отчёте: `runAction.js` (канонический диспетчер) реально вызывает `game.applyAction(state, action, context)` — **тремя** аргументами, с `context` (несущим `rng`). Last Sector's собственная функция принимала только два параметра и жёстко подставляла `{}`, теряя уже переданный контекст. Это не архитектурный выбор между двумя вариантами, а потерянный параметр.

**Что сделано:** функция теперь принимает и пробрасывает `context`. Подтверждено вживую: вызов через канонический `runAction()` и прямой вызов `applyAction()` с реальным контекстом оба работают корректно. 3 новых теста, включая проверку, что функция по-прежнему корректно отклоняет вызов **без** контекста (не изобретает случайный RNG незаметно для вызывающего).
